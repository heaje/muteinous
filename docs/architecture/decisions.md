# Architecture decision log

**Project:** Muteinous v2 — redesign of the profanity-filtering application. First supported content: video games; future content types should be possible without building speculative interfaces now.

**Status:** Architecture exploration in progress. This is a record of decisions made in conversation, not a finalized architecture or implementation plan.

**Platform direction:** Windows first, with eventual support for Linux and macOS. Preserve portability in domain models, shared scanning, audio editing, and installation safety. Keep OS-specific game discovery, GPU backends, native tool execution, case/encoding/path behavior, and packaging behind narrow boundaries. Support for any specific game, mod technique, external tool, or GPU on Linux/macOS will require separate verification; cross-platform UI/runtime support does not imply all games are supported. **Primary implementation language: Python (D25).**

**Source repositories:** [Existing implementation](https://github.com/heaje/hushpatch) · [Target repository](https://github.com/heaje/muteinous)

**Record opened:** November 20, 2026. No repository changes are authorized by this log.

## Agreed decisions

### D01 — Simpler installation recovery

**Status: Agreed.** Protect original files and preserve a reliable manual repair/restore path; do not require automatic reconciliation of every interruption. Partial installation after a crash is acceptable, irretrievable loss of original data is not. Back up originals and make recovery information durable before replacing originals; detect incomplete/uncertain states and stop rather than guessing. Do not inherit the existing multi-layer journals and recovery framework by default.

### D02 — Shared installation authority

**Status: Agreed (Option B).** Content plugins prepare and stage modifications; shared installation infrastructure exclusively performs writes to user-owned content. The shared component should be small and focused on path validation, authorization/ownership, backups, safe replacement/removal, manual restoration, and D141's pre-write running-game safeguard based on generic OS/installation evidence. Plugins may write to staging areas. In-process Python plugin APIs are not a security sandbox: dependency rules, tests, review, and controlled integration paths are needed to enforce this architectural boundary.

### D03 — Minimal plugin contract with optional capabilities

**Status: Agreed (Option B + anti-overengineering principle).** Use a small common plugin contract, with optional capabilities only where genuinely distinct, evidence-discoverable native-format or installation capabilities demonstrate variation. Do not create interfaces for hypothetical audiobook/movie behaviors. One video-game content plugin can own its game-engine adapters and generic launcher/OS installation discovery internally under D137; this must not introduce curated game lists or per-title discovery rules. Prefer explicit built-in registration initially; no speculative dynamic SDK/compatibility framework. Abstractions must have a real consumer and a justified variation.

### D04 — Content-neutral Segment

**Status: Agreed (Option B).** A minimal, content-neutral `Segment` is the core unit of filterable content. Keep native file paths, codecs, asset grouping, archive details, and reconstruction metadata private to the plugin. Keep transcription output distinct from text actually present in the source; inferred speech is not automatically editable subtitle text. Exact `Segment` fields are **not yet finalized**.

### D05 — Strict audio fidelity and engine compatibility

**Status: Agreed (Option A).** Use the highest-fidelity decoded source for edits; reduced-quality analysis copies must never become final editing sources. Preserve sample rate, channel count/layout, precision, duration/sample count, native codec/container structure and engine-relevant identifiers unless a known format requires otherwise. For uncompressed PCM, preserve samples outside defined edit regions bit-for-bit where technically possible. For lossy sources, re-encoding may inherently alter decoded samples; minimize avoidable loss, preserve native compatibility, and validate rebuilt artifacts. Do not install outputs when native asset format/codec/structural compatibility cannot be established with sufficient confidence. Separately, D135 permits an explicitly approved, non-destructive and reversible experimental *loader-acceptance* test when the native outputs have passed all applicable validation; this does not relax any native compatibility or fidelity check.

### D06 — Bounded temporary WAV workflow

**Status: Agreed (Option A).** Use uncompressed PCM WAV temporary working files, not a new in-memory PCM interface. Decode/process a small number of clips or assets at a time; begin sequentially and only add limited concurrency if needed. Delete scratch WAVs after reconstruction, and safely clean abandoned scratch files on future runs. Preserve compact scan results (transcription, word timing, decisions), not a full library of decoded WAVs. Original backups and staged native outputs have separate lifetimes. Avoid a complex cache manager.

### D07 — Plugin-owned native asset grouping

**Status: Agreed (Option B).** Filtering decisions refer to segments; the plugin groups affected segments by native asset and rebuilds each affected asset once. Avoid unnecessary changes to unrelated clips/assets, especially unnecessary lossy re-encodes. No public core-level `AudioBank` / `AssetGroup` / `RebuildUnit` abstraction unless demonstrated by a concrete requirement.

### D08 — Plugin coordinates reconstruction; shared audio functions perform censorship

**Status: Agreed (Option B).** The core decides what is censored. The plugin coordinates extraction, source-quality temporary WAVs, grouping by asset, invocation of shared PCM censoring functions, native reconstruction, format-specific validation and staging. Shared installation infrastructure performs the final write. Under D146, the same shared PCM censorship functions may also generate bounded temporary, non-installed original-versus-censored audio previews. The plugin must not reimplement filtering policy or the audio censor algorithm. An illustrative minimal operation is `prepare_changes(edits, staging_dir)`; the final signature and edit schema are not yet agreed.

## Working boundaries (not independently finalized)

- The plugin supplies decoded audio when needed, while analysis services may derive lower-rate copies for transcription/alignment.

- The core owns filtering policy, word matches, user choices and edit decisions; game plugins own format details.

- A shared set of audio editing functions performs sample edits, while plugins invoke them in an asset-appropriate order.

- Shared installation utilities must be narrow; avoid a general-purpose transaction framework.

## D09 — Core passes concrete editing instructions

**Status: Agreed (Option B).** The core resolves matches, presets, and user decisions into concrete edit instructions (e.g., audio time ranges, text character ranges where source text actually exists, and censor styles). Scanning and review are separable from applying censorship: users may explicitly request a content scan first, inspect available source-backed text, distinctly labeled inferred speech transcripts and D152 user-corrected transcript annotations, and detected matches, preview uncertain speech assets and locally confirm their role under D136 where supported, review evidence-based voice/subtitle links and locally confirm uncertain associations under D140, search/filter scan results and hear D146's suggested or user-selected original-versus-censored previews, mark missed audio censorship ranges with explicit source-bound confirmation under D147 where supported, adjust censorship settings and individual decisions, including D157's explicitly confirmed, validated bulk review changes with D156 session Undo, explicitly export/import eligible preferences and valid review decisions under D148, and only then explicitly request preparation and installation. A censorship preset need not be finalized before scanning; valid source scans and speech analysis may be reused while the core recomputes affected filtering decisions and edits (D45). Plugins do **not** evaluate objectionable-language policy or user preferences. They use the instructions to coordinate fidelity-preserving PCM editing, native asset grouping, reconstruction, validation and staging. Source-backed text must be distinguished from inferred transcripts. The exact instruction types, timestamps/offset conventions, and validation contract are **not yet finalized**. **D159 phases this broader review/editing design:** the initial release provides automated scanning, detected-content inspection, safe audio preview, words/settings, and explicit Apply; advanced occurrence-by-occurrence editing and review tools above remain agreed for later releases.

## D10 — Reject edits when scanned source content changes

**Status: Agreed (Option A).** Before applying stored editing instructions, verify that the underlying source content is still the content scanned. If relevant original content has changed, refuse stale edits and require a new scan of that content. Do not automatically remap old timestamps or text ranges. User preferences and word lists may persist across rescans. **See D11** for asset-scoped invalidation; exact fingerprint/validation contract remains unresolved.

## D11 — Invalidate scan results by affected source asset

**Status: Agreed (Option B).** Preserve cached scan results for unaffected source assets; when an original asset changes, invalidate and rescan the segments that depend on it. Plugins know their native assets and segment relationships. Avoid a general dependency-graph or update-remapping framework. If the plugin cannot reliably identify affected content, invalidate a broader scope (up to the entire scan) rather than reuse results unsafely. Changes solely to audio censorship settings preserve otherwise-valid scan and speech-analysis results under D45. This preserves existing hushpatch incremental-scanning behavior in principle. **See D12** for fingerprint ownership; the minimal representation of segment-to-source dependencies remains open.

## D12 — Plugins identify and fingerprint source assets

**Status: Agreed (Option A).** Each content plugin defines stable source-asset identities, knows which segments rely on each asset, and provides content fingerprints for those source assets. Shared scanning infrastructure stores/compares those fingerprints and invalidates affected cached results when they differ. This must not expose native game-archive details to the filtering domain. Prefer straightforward content hashing and comparisons over a version-management framework. **A source fingerprint is not authorization to install:** shared installation infrastructure independently checks destination safety before writing. **See D13** for segment identity ownership and **D14** for reading verified originals when an in-place modification is installed.

## D13 — Plugins assign stable opaque segment IDs

**Status: Agreed (Option A).** Each plugin assigns segment identifiers derived from its knowledge of native filterable occurrences; the core only stores and compares identifiers, without interpreting archive paths, clip indices, engine metadata, or their internal structure. IDs must disambiguate repeated identical dialogue and remain stable across rescans of the same logical segment when feasible; they must not depend merely on discovery order. A segment's identity is separate from the source asset fingerprint used to determine scan validity. **Identifier scope settled by D28:** IDs are unique within a content item and independent of installation location. The application must retain the content-item context when combining or persisting segments from different content items.

## D14 — Scan original content, not installed censored replacements

**Status: Agreed (Option A).** Scanning must always use original game content. For non-destructive standalone mods, read the underlying unmodified assets; for in-place installations, read verified original backups. Original source fingerprints must refer to the original bytes/content, not Muteinous-generated censored replacements. If required originals or backups are missing, corrupt, or cannot be verified, stop with a clear error rather than silently scanning modified assets. Rescanning after changing filtering settings should not require restoring original game files to the installation. **See D15** for shared verification of originals. D142 resolves game updates during managed installations: detect changed original/source or managed destination state, preserve verified backup/recovery evidence, and never restore an outdated backup over updated game content; require verified user-initiated recovery or regeneration.

## D15 — Shared infrastructure resolves verified originals for plugins

**Status: Agreed (Option A).** The plugin identifies which original native source file it needs but does not independently select or verify an in-place backup. A narrow, read-only shared operation checks the recorded installation/backup state and provides access to the verified original or verified backup, as appropriate. If the original cannot be established reliably, refuse access rather than silently returning a censored or ambiguous file. The plugin then decodes and interprets native content normally. This boundary centralizes original-backup safety without creating a new source-management framework. Exact function signature and ownership of short-lived read handles/paths remain open.

## D16 — One video-game content plugin with internal engine adapters

**Status: Agreed (Option B).** The public plugin boundary represents content types, not individual game engines. Initially there is one video-game content plugin. It encapsulates generic launcher/OS installation discovery and manual-folder intake (D137), installation scanning, evidence-based format and engine identification, reusable native-format/engine adapters, native asset reconstruction and validation. Adapters are selected by detected capabilities, not by game title, store ID, or any curated game registry (D132–D133). Unreal, Falcom, Wwise and other game-engine implementations remain internal ordinary Python code rather than independent public plugins. The content-neutral core sees only the common plugin-facing contract; future audiobook/movie types may implement that contract without adopting game-engine abstractions. Do not introduce a second general plugin architecture for the internal engine adapters. **See D17** for destination proposals. The precise staged-output/installation plan contract and minimum public capabilities remain open.

## D17 — Plugins propose destinations; shared installation infrastructure validates and writes

**Status: Agreed (Option A).** From scan-derived installation evidence and reusable, verified format/loader rules, the plugin proposes installation-specific placement of staged native artifacts, including whether a new standalone mod output is supported or a verified original may be replaced. No named-game path tables, hardcoded mod locations, or title-based installation assumptions are permitted. Without adequate evidence of a safe candidate destination and installation method, the capability is unavailable under D132–D133; D135 narrowly allows explicit testing when only actual game-loader acceptance remains unverified, and the proposed installation is demonstrably non-destructive and reversible. These proposals confer no authority. Shared installation infrastructure independently checks installation identity, allowed destination roots, path safety, existing-file ownership/conflicts, write type, and D141's applicable game-running state before performing writes. The core filtering domain does not contain game-specific paths or mod-placement logic. **See D18** for the small declarative installation-plan contract.

## D18 — Plugin returns small declarative installation plan

**Status: Agreed (Option A).** The plugin prepares native reconstructed output files in staging and returns a declarative list of staged artifact, proposed destination, and intended operation (create/manage a generated output or replace an original under verified backup protection). These reconstructed native outputs awaiting installation are validated, protected installation-staging artifacts, not automatically immutable published reusable analysis/result-cache bundles under D105–D110. Keep each staged artifact safely associated with its still-valid prepared installation plan until installation completes or the plan is rejected, cancelled, or safely disposed of; never allow cleanup or another job to remove or replace a staged artifact while an authorized installation may still consume it. This distinction does not relax D24's complete preparation/validation requirements or shared installer authority. The shared installer validates the complete plan before changing user-owned files and exclusively performs approved writes, removes, and restores. For D143 explicitly selected partial coverage, bind the plan to the precise selected supported scope and its source/coverage validity so an excluded, unverified, or failed required edit cannot be silently presented as a successfully completed requested edit. For D135 experimental loader-acceptance tests, the plan must identify its experimental status and evidence sufficiently for the shared installer to enforce explicit per-attempt approval, safe ownership/placement, and demonstrably non-destructive, reversible operations; this does not waive preparation or native-output validation. Plugins must not invoke arbitrary install/delete operations themselves. The plan is not a general-purpose transaction framework; interrupted installation may leave partial applied changes if verified originals can be recovered. The exact data type, error reporting, ownership record, and allowed operations should be kept minimal and informed by demonstrated reusable native-format and installation capabilities, never curated game definitions.

## D19 — Small per-installation manifest for ownership and recovery

**Status: Agreed (Option A).** Shared installation infrastructure maintains a small manifest for each managed installation, not a global append-only ownership ledger. Record managed destinations, operation type, verified original-backup locations and hashes where applicable, the hashes of installed outputs, the effective audio-settings snapshot for filtered installed outputs (D43), the compact effective language-outcome fingerprint for installed filtering (D61), a compact deterministic fingerprint of the effective required censorship-edit outcome actually installed (D42/D44), and enough durable completion/incomplete-state information to guide safe manual restoration. Persist the information necessary to recover the original **before** any destructive replacement. Use the manifest to prevent deleting or overwriting unexpected third-party changes and to support uninstall/restore. Under D142, compare managed destinations and relevant original/source dependencies against recorded identities/hashes when an update is detected; preserve existing recovery evidence, mark affected status uncertain/outdated, and never use a stale backup to overwrite changed or updated game files. The manifest need not preserve a detailed event history or power automatic transaction reconciliation. Exact schema, on-disk location, and atomic persistence mechanics remain implementation decisions to be justified by supported installation modes.

## D20 — Keep Segment content-neutral; store source dependencies in scanning metadata

**Status: Agreed (Option B).** Segment carries only identity (D27); do not include source file paths, asset IDs, fingerprints, archive data, or segment-to-asset dependencies directly on the domain object. The video-game plugin supplies segment-to-source-asset associations as separate scan metadata. Shared scanning infrastructure compares asset fingerprints and invalidates only segments whose dependencies changed, retaining unaffected scan results. This association may be implemented as simple keyed mappings rather than a general dependency graph. D140 also keeps discovered or locally confirmed speech-to-source-subtitle relationships in small scan metadata mappings with source validity, not on identity-only `Segment`. D62 also permits tracking relevant language-evidence validity separately where necessary for targeted language reassessment, reusing these simple associations without introducing a general dependency graph. Exact source-backed text is stored in a scan-scoped segment-ID mapping (D30), separate from dependency metadata. Per-occurrence language assessments and filtering/coverage outcomes may also be retained as separate existing scan metadata under D61, not fields on `Segment`. Scan-metadata types, plugin protocols, and installation descriptors remain drafts to review together.

## D21 — Keep ASR transcripts and word timings in separate scan results

**Status: Agreed (Option A; source-text location amended by D27).** Actual editable text present in the source content (for example, a subtitle) is stored in a scan-scoped mapping from segment ID to exact source text (D30), separately from the identity-only `Segment` object. An occurrence without such text has no source-text record. Inferred audio transcription is a scanning result associated with that segment identity and must not be treated as editable source text. D152 permits separate source-bound user transcript-correction annotations for review/search, not replacements of the original recognition result or verified source text. A speech-specific immutable `SpeechAnalysisResult` groups recognized transcripts and word-level alignment/timing data for each analyzed speech segment (D31); these are analysis outputs rather than original content. The core can use transcripts and timings to decide audio censorship spans without mistakenly requesting nonexistent subtitle edits. **Speech-analysis result grouping is settled by D31; immutable word-timing objects with word text and segment-relative `float` start/end seconds are settled by D66. Other exact fields and result storage remain open.**

## D22 — Audio instructions use time ranges; shared PCM editor resolves sample frames

**Status: Agreed (Option A).** The core expresses audio censorship spans in time units relative to the segment's decoded audio, rather than sample-frame indices tied to a particular source rate. Shared audio editing functions convert these intervals to sample-frame boundaries using the actual original-quality working WAV sample rate. Define intervals as start-inclusive/end-exclusive; reject out-of-bounds or invalid intervals rather than silently moving edits. Under D147, explicitly user-confirmed manual audio ranges follow the same segment-relative interval and boundary validation without being represented as invented ASR word timings. This maintains independence between speech analysis/alignment and native sample rate while allowing precise PCM edits. **Word timing representation is settled by D32 as segment-relative Python `float` seconds; sample-frame boundary rounding is settled by D33 as floor(start) and ceil(end). Still open:** segment-to-native-asset time mapping owned by plugins.

## D23 — Text edit ranges use Python Unicode string indices into exact source text

**Status: Agreed (Option A; source-text location amended by D27).** Core text editing instructions identify start-inclusive/end-exclusive Unicode code-point ranges (Python string indexing) relative to the **exact** unnormalized source-backed text retrieved from the scan-scoped segment-ID-to-source-text mapping (D30), not a field on `Segment`. No native encoding, byte-offset, or serialized game-file position details are exposed to the core. The plugin maps validated ranges to its native text representation, preserves native encoding/structure where technically possible, and rejects edits that no longer match the original. Editing boundaries must not split user-perceived grapheme clusters or otherwise corrupt Unicode. Transcripts inferred from audio remain in separate scan results and cannot generate native text edits unless corresponding source text exists. **Still open:** concrete `TextEdit` schema, Unicode grapheme-boundary validation mechanics and how native constraints affect masking/replacement styles.

## D24 — Native reconstruction and validation must all succeed before installation

**Status: Agreed (Option A).** A plugin may return its installation plan only after **all** requested affected native assets within the user's explicit selected scope (which may be a supported subset under D143) have been reconstructed successfully and validated for engine compatibility and the fidelity constraints established in D05. If preparation or validation fails for any required asset, the preparation step fails as a whole and **no installation plan is accepted or executed**. Staged scratch artifacts may be discarded; the user's game installation remains unchanged. Surface the specific failed asset and actionable failure reason. Do not silently omit failed edits or install only the successful subset of requested edits; D143 permits an explicitly chosen, independently safe partial-coverage scope **before** preparation, not post-failure shrinking of that scope. Occurrences intentionally excluded or only partially filterable under language-coverage decisions D51–D55 are not failed required native edits merely because coverage is incomplete; D57 governs their non-blocking installation warnings. An otherwise validated prepared plan is additionally rejected at installation time if its effective audio settings are stale (D44), effective language assessments/coverage outcomes used to prepare it are stale (D60), or an intervening game update has invalidated source or installation assumptions under D10/D142. This applies to failures **before installation**, and does not replace the earlier simpler recovery policy for a failure after an already-validated installation begins.

## D25 — Python-first with replaceable compiled components

**Status: Agreed, conditional on narrow replacement boundaries.** Python is Muteinous v2's primary implementation language, initially targeting the Python version compatible with the chosen mature dependencies (the existing project currently uses 3.12). Do not rewrite the whole application in Go or Rust merely for native compilation. Maintain OS-portable domain models and core interfaces (Windows first, Linux and macOS later). Use mature compiled libraries for inference/codecs. Organize work so a demonstrated bottleneck or safety-sensitive component (e.g., native asset parser/rebuilder, PCM editor, or speech backend) can later be replaced by a compiled implementation behind a focused, testable interface without changing `Segment`, concrete editing instructions, installation plans, or unrelated core components. Favor existing file-based staging/WAV interfaces and ordinary data types; choose a small Python binding/wrapper or subprocess per actual need. Require behavioral parity tests, native-format fidelity and safety validation. **Do not construct a speculative native plugin SDK or generic FFI framework now.** 'Easy to swap' is an architectural goal, not a promise that porting and packaging will require no engineering. Revisit this decision only upon demonstrated evidence of a better alternative.

## D26 — Segment represents any independently filterable occurrence

**Status: Agreed (Option A).** `Segment` is the content-neutral identity of any independently filterable occurrence, not just a spoken or written line. It may represent dialogue, editable source-backed text, a visual event, a full scene, or audiovisual content. This is conceptual scope for extensibility, **not** authorization to implement video or movie filtering now. Keep native media details, visual-analysis metadata, timestamps and source dependencies outside the minimal `Segment` unless a separately reviewed concrete requirement justifies otherwise. This decision does **not** settle the exact `Segment` fields, editing-instruction schemas, video analysis interfaces, or timeline-editing behavior.

## D27 — Keep Segment as an identity-only class

**Status: Agreed (Option A).** Retain a small, immutable Python `Segment` domain class containing only an opaque plugin-assigned `id: str` (illustratively `@dataclass(frozen=True, slots=True)`). It represents the identity of any independently filterable occurrence as established in D26, without `source_text`, `has_audio`, video fields, native-format data or source dependencies. Store exact source-backed text, when present, separately and associate it with the segment identity; keep inferred ASR transcripts, word timings, and future visual analysis separate from source-backed data. Editing instructions and source dependencies refer to segment identities. This explicitly amends only the storage-location wording of D21 and D23; their source-versus-inference distinction and Unicode code-point range rules remain established. **ID scope is settled by D28 (content-item-scoped). Still open:** specific source-content/scan schemas, concrete edit types and plugin signatures. Do not add an independent `SegmentId` wrapper or broader media framework without a demonstrated need.

## D28 — Segment identifiers are scoped to a content item

**Status: Agreed (Option B).** Each plugin assigns a stable, opaque segment ID that is unique **within its content item** (for example, one game), regardless of installation path or which installed copy is scanned. Different content items may use the same segment ID. Shared scanning and storage must carry the content-item context when combining or persisting data across content items, so equal IDs from unrelated items are never treated as the same occurrence. Multiple installations of the same content item may refer to the same logical segment IDs, but scan validity, source fingerprints and installation safety remain independently verified against the applicable original assets and installation state; identity alone never licenses cache reuse or writes. Keep `Segment` as the D27 identity-only class without adding installation information or native paths to it. **Content-item semantics settled by D29:** content IDs represent plugin-defined compatible occurrence namespaces; editions, localizations and versions share a content ID only when occurrence identity remains reliably compatible. **Still open:** exact ID format and concrete cache-key schemas.

## D29 — Content IDs identify compatible occurrence namespaces

**Status: Agreed (Option A).** A content ID is a stable, opaque identifier derived by the content plugin from reliably observed source/format evidence to identify a **compatible occurrence namespace**; it must not be looked up in a maintained game, edition, or storefront catalog (D132–D133). It is independent of installation paths and storefront/store installation identities. Ordinary game updates may keep the same content ID if the plugin can reliably identify the same logical occurrences across versions; editions or localizations may share it only when their segment identity mapping remains compatible. When equivalence cannot be established reliably, the plugin must use a distinct content ID rather than risk collisions or misassociated filtering decisions. Each segment remains identified within that content item (D28), so combined storage or processing must retain both the content context and segment ID. Keep installation identity and original-asset content fingerprints separate: a shared content ID does not establish identical original bytes, safe cached-analysis reuse, or permission to install. No global identity registry or speculative compatibility framework is required. **Still open:** concrete `content_id` representation, how compatibility is verified from generic scanned evidence, and exact persistence/cache-key schemas.

## D30 — Scan-scoped mapping for exact source-backed text

**Status: Agreed (Option A).** Represent exact, unnormalized, source-backed editable text as a simple mapping from segment ID (`str`) to source text (`str`), scoped to a particular scanned original-source snapshot. Only segments with actual source-backed text have entries; absence does not imply that the occurrence lacks audio or visual content. Keep `Segment` immutable and identity-only (D27); do not add a `SourceText` class or generalized multimedia source-content model without a demonstrated need. Within the snapshot, the enclosing content-item context disambiguates segment IDs (D28–D29). The mapping must not be treated as globally valid merely because content and segment IDs match: source fingerprints, installation/original-source context and scan validity govern reuse (D10–D15). ASR transcripts and word timings belong to speech-specific `SpeechAnalysisResult` objects (D31), while future visual analysis remains separate (D21), and native asset references/dependencies remain separate scanning metadata (D20). Text edits use D23 Unicode ranges against the exact mapped string. **Still open:** concrete scan-result and snapshot containers, persistence/cache keys, and dependency schemas.

## D31 — One immutable SpeechAnalysisResult per speech segment

**Status: Agreed (Option A).** Represent speech-analysis output with one small, immutable `SpeechAnalysisResult` per analyzed speech segment, associated by its segment ID and containing the recognized transcript and word-timing information. Keep the transcript and timings together as a coherent result rather than separate result classes or scan-scoped mappings. Under D152, user-corrected transcript annotations belong to separate local review metadata and do not mutate or overwrite this immutable recognition result. This type is specific to speech analysis, not a universal `ScanResult` container; other modalities may use their own analysis outputs if and when needed. `Segment` remains identity-only (D27), and exact source-backed text remains in the scan-scoped mapping (D30); ASR-derived text must not be substituted for verified original source text (D21). Source dependencies, fingerprint-based validity, and the speech-analysis input signature (D46) remain separate scanning/cache metadata (D20, D10–D15). Processing and failure states may be handled outside the immutable result; no processing-state schema is established here. **Word timing units are settled by D32 as segment-relative Python `float` seconds, individual immutable word-timing objects by D66, optional provider-specific alignment scores by D67, validation of word intervals and contextual speech-result timing under D68, and PCM sample-frame rounding by D33. Partial speech-analysis preservation and required-edit safety are settled by D69; D71 supersedes D70's separate unaligned-word mapping with one ordered immutable sequence whose word timestamps may be absent as a pair. Still open:** remaining Python field types, provider-specific alignment behavior, scan-result storage and cache keys.

## D32 — Floating-point seconds for segment-relative word timings

**Status: Agreed (Option A).** Represent recognized word start and end times as Python `float` values in seconds relative to the segment's decoded audio. This applies to the immutable per-word timing objects within `SpeechAnalysisResult` (D31, D66). Use start-inclusive/end-exclusive intervals, consistent with D22. Shared audio editing functions convert time ranges to sample-frame boundaries using the actual working WAV sample rate, rather than exposing sample-frame positions in analysis results. Reject invalid or out-of-bounds intervals rather than silently adjusting them. Floating-point numerical precision is sufficient for sample-level audio work; the quality of word-boundary alignment is a separate concern and is not guaranteed by the timestamp representation. **Sample-frame rounding is settled by D33 as outward rounding. Still open:** handling of uncertain boundaries and optional padding/fades, and segment-to-native-asset time mapping.

## D33 — Round audio censorship boundaries outward to whole sample frames

**Status: Agreed (Option A).** When shared PCM audio editing converts a start-inclusive/end-exclusive censorship interval expressed in seconds to sample-frame boundaries, use `start_frame = floor(start_seconds * sample_rate)` and `end_frame = ceil(end_seconds * sample_rate)`, with the actual working WAV sample rate. This covers the full requested interval, possibly including less than one extra frame at either boundary. Continue to reject invalid or out-of-bounds intervals rather than silently clamping them (D22); preserve unaffected audio. This is a boundary-quantization rule, not a guarantee that speech alignment identifies perfect word boundaries. **User-configurable before/after padding is established by D34; it is applied before sample-frame conversion and may overlap neighboring word boundaries. Still open:** default padding values, fade behavior, and segment-to-native-asset time mapping.

## D34 — User-configurable before/after censorship safety margins

**Status: Agreed (Option B).** Support independently user-configurable before-word and after-word safety margins for audio censorship. The core applies these margins to the recognized word intervals when producing censorship time ranges; plugins do not independently implement or choose padding policy (D08–D09). Margins may extend across reported neighboring word boundaries, prioritizing complete censorship even if a small portion of adjacent acceptable speech is also affected. Limit optional padding at segment boundaries as specified by D35; reject intrinsically invalid or out-of-bounds word/edit intervals under D22. Convert valid intervals to sample frames using D32–D33. This policy compensates for possible alignment imprecision but does not establish that padding fixes alignment, time-offset, or fade bugs. **Still open:** default margin values, permissible user adjustment ranges, configuration persistence and UI, overlap/merging details and fade behavior.

## D35 — Limit audio censorship safety margins to segment boundaries

**Status: Agreed (Option A).** When applying user-configured before/after safety margins (D34), limit the expanded censorship interval to the segment's valid decoded-audio time bounds, retaining as much requested padding as fits. **Video-game plugin growth path.** Begin flat, as above. ## D161 — Keep routine test execution fast with explicit CI budgets

**Status: Agreed (initial test-performance policy).** For the **required pull-request test suite**, target **at most five minutes of test execution** on the baseline **two-vCPU Windows GitHub Actions runner**, measured consistently and excluding unrelated runner provisioning, dependency installation, and packaging/setup overhead. Treat five minutes as a performance target and investigation threshold, not a reason to delete, weaken, or silently skip tests. Enforce an approximately **ten-minute hard timeout for the required PR test execution** through an appropriate CI/test-runner mechanism; a timeout must **fail** the required check, not be reported as success or as a completed test suite. Configure CI so setup/runtime accounting and failure reporting are understandable; do not claim a job-level timeout isolates test execution when that timeout also covers setup.

Organize tests by purpose as established in D160: fast unit and plugin-contract tests, plus deterministic **safety-critical integration coverage**, run on every PR; longer native-format, real-inference/model/hardware, cross-platform, large-fixture, recovery/failure-injection, and end-to-end validation may additionally run on main-branch, scheduled, or release-candidate workflows when justified. Keep representative source validity, stale-edit rejection, required-edit completeness (D24/D143/D159), PCM fidelity/timing, installation ownership/backup/recovery, and storage-integrity protections in the required PR checks using small synthetic fixtures and controlled fakes where necessary. **Do not defer all safety testing to nightlies**, or accept unrun, skipped, incomplete, or timed-out required checks as passed. Comprehensive release validation must exercise all applicable supported behavior despite its longer budget.

Prefer cheap, deterministic fixtures and fake inference providers for routine checks; separately gate genuine model downloads, GPU, native tools, and real-format exercises in correctly provisioned environments. On the two-vCPU runner, benchmark serial execution and modest parallelism (for example, two workers) rather than assuming more workers are faster. Track total suite runtime and slow tests (for example, `pytest --durations`), investigate sustained regressions above the five-minute target, and adjust fixture design, test boundaries, or CI tiering **without hiding lost coverage**. Any justified revision to the baseline budget or required checks must be explicit and reviewed, rather than silently increasing timeouts or excluding tests. This decision sets test-execution policy, not new production functionality or a fixed limit on comprehensive/release suites.

## D162 — Defer manual speech-role and voice/subtitle relationship confirmations from initial release

**Status: Agreed (initial-release scope clarification of D159; D136 and D140 remain agreed for later).** Defer **user confirmation or rejection of uncertain speech roles** under D136 and **user confirmation or rejection of inferred voice/audio-to-subtitle relationships** under D140 from the initial release. Do not build their manual-confirmation UI, approval persistence, or special confirmation workflow merely in anticipation of a later release.

**Retain automatic evidence processing.** During an explicitly requested scan, continue D139's bounded, evidence-based speech-candidate assessment and appropriate automatic speech analysis, and D140's generic, evidence-based discovery of native audio/text relationships where supported. Keep verified native relationships distinct from plausible inferred associations, uncertain speech roles and unmatched content; display limitations and coverage honestly in read-only results. Analyze and filter independently supported audio and actual source-backed text separately where their own evidence is sufficient; a relationship between them is **not** universally required to censor either modality safely.

**Preserve refusal safeguards.** Never turn an uncertain role or merely plausible association into verified evidence, invent word timings or source-backed subtitles, or treat a missing user confirmation as granted. When unresolved speech role or association is **actually required** to determine or safely complete a censorship edit within the user's explicitly selected scope, report the limitation and refuse preparation/installation of that scope until a supported path is available. An independently supported subset may still be explicitly chosen beforehand under D143/D24; an absent or uncertain link alone must not block otherwise independently safe audio/text editing. Preserve all D159 freshness, fidelity, required-edit completeness, language-coverage and installation protections. D136/D140 manual confirmations remain later-phase design, not rescinded requirements; no new mandatory content-plugin contract or game-title-specific knowledge is introduced.


## D163 — Use Go Task as the cross-platform development command interface

**Status: Agreed (development tooling).** Use [Go Task](https://taskfile.dev/) with one root `Taskfile.yml` as the consistent local command interface for Windows, Linux, and macOS. Prefer portable invocations and Task's native OS conditions for genuinely differing commands; split Taskfiles or add small Python helpers only when demonstrated complexity justifies it. Do not introduce a Makefile or a second competing task runner.

Expose explicit `setup`, individual lint/format-check/typecheck/test/build/version-preview commands and a comprehensive `check` covering routine required local validation. GitHub Actions may run individual tasks to preserve separate reporting, timing, and failure attribution; workflow-specific permissions, orchestration, and release gates remain in GitHub Actions. `task check` need not run expensive hardware/model/native-format or release-only tests. Ensure normal tasks do not silently install dependencies or create environments: `task setup` explicitly prepares the locked environment under D164; other tasks use it without requiring shell activation and fail clearly when setup is missing. Clean tasks must avoid deleting user data or untracked valuable files.

This is the chosen future command contract, not a claim that the current repository already contains a Taskfile. Preserve D160's single Python package and D161's independently measured test execution and timeout requirements.

## D164 — Use the newest verified Python series and locked uv dependencies

**Status: Agreed (Python and dependencies).** Support **one Python minor series at a time**, chosen as the newest stable CPython release verified compatible with **all required application libraries, native extensions, inference/GUI integrations, build tooling, and supported platforms**. Python **3.14 is the provisional target**, subject to real dependency resolution and test evidence; use the newest compatible patch release of the selected series. Advance to Python 3.15 only after equivalent verification, and do not use prerelease interpreters for official builds. The earlier Hushpatch dependencies are inputs for compatibility investigation, not automatically adopted Muteinous v2 requirements. If 3.14 cannot be verified, record exact blockers and request a reviewed policy adjustment rather than claiming support. Do not keep an older compatibility range solely for hypothetical pip users; official standalone packaging will carry its own runtime when implemented.

Use [uv](https://docs.astral.sh/uv/) for explicit `.venv` setup and commit a **cross-platform `uv.lock`**. Local development and CI must install from the lock rather than independently resolving dependencies; [`pyproject.toml`](../../pyproject.toml) retains suitable compatible dependency constraints, including actual build/tooling dependencies. Pin or otherwise control versions needed for verified releases. Dependency resolution must account for platform-specific wheels and native binaries, without assuming Linux/macOS application support from a successful portable installation.

Use **Dependabot** for weekly grouped Python/uv and GitHub Actions maintenance updates, with security updates handled separately. Require Conventional Commit-shaped update titles/messages, CI and review as appropriate; **no auto-merge**. Do not treat Dependabot automation as a substitute for verifying native/inference compatibility. Migration from the current Python 3.11+ declaration and 3.12 Windows CI is implementation work, not a completed change.

## D166 — Version and publish intentionally through Git tags and draft GitHub Releases

**Status: Agreed (versioning, builds, release policy).** Require **Conventional Commits** for each commit **and PR title**, checked in CI rather than relying only on squash-merge titles. Use **Commitizen** to propose release versions and generate release notes, **setuptools-scm** for Python package versions derived from Git tags, and Git tags as the canonical version identifiers. Do not manually edit a package version, maintain changelog fragments or a committed `CHANGELOG.md`, or implement a home-grown version calculator. Development package versions produced by setuptools-scm can legitimately differ from Commitizen's proposed next release target. Before version 1.0, configure breaking changes to normally increment the minor version; graduation to **1.0.0** (including any prereleases) requires a separate approved architectural-policy and configuration change.

**Manual initiation and channels.** A manually triggered GitHub Actions release workflow asks for alpha, beta, RC, or stable; it derives and validates the proposed version and next prerelease number using Conventional Commits and existing tags. Default to releasing from `main`; make a dedicated `release/*` stabilization branch only when warranted. Each channel receives its **own** Git tag, fresh source validation and package builds from that tag, even if the source revision matches an earlier prerelease. Official releases create **draft GitHub Releases** with editable Commitizen-generated notes; publication is an explicit subsequent human action, never automatic. GitHub Releases are the **authoritative changelog and sole official distribution channel** for wheels and sdists; do **not** publish to PyPI. Standalone Windows installer packaging is selected and added only when the desktop app exists; Linux/macOS application artifacts require separate validation.

**Development artifacts.** Downloadable development wheels/sdists are built and uploaded **only on manual request**, not after every merge or nightly. Use the GitHub repository's configured Actions artifact retention, with **no workflow `retention-days` override**. Record build provenance for development artifacts as well. Routine CI may validate package builds without uploading retained artifacts.

**Integrity, failure recovery, and implementation simplicity.** Build and validate from a known Git SHA/tag with locked dependencies; record source SHA, release tag (for official releases), package/version, Python version, build environment and SHA-256 checksums with release artifacts. Do **not** require independent byte-for-byte rebuilds or GitHub artifact attestations. Before tagging or drafting, validate source, commit history, tag/version consistency, required CI/test results and packaging readiness. Official release validation must also cover all applicable supported behavior under D161; routine portability checks alone are not sufficient. A failed **unpublished** release may exceptionally be deleted/reset and its version tag recreated after a fix, but only through an **explicit, auditable** recovery operation that confirms it has never been published and avoids silent reuse or overwrites; document the risk of tags already fetched by others. **Published tags must not be moved or reused.** Use GitHub's official maintained actions where available, suitable maintained third-party actions when justified, and `gh` or minimal scripts where simpler, with least-privilege permissions and understandable diagnostics. Avoid speculative release infrastructure.

All mechanisms in this decision are **requirements for subsequent implementation**, not evidence that versioning, tagging, release workflows or repository protections are already deployed.

## Process rules

- Discuss and settle one substantial architectural decision at a time.

- Separate **agreed**, **working proposal**, and **open question** clearly. Do not silently promote a proposal into a decision.

- No repository edits or implementation until the architecture is explicitly agreed.

- Update this decision log as new decisions are confirmed. When the architecture is approved, consider committing a Markdown/ADR version to the new repository as the version-controlled long-term source of truth.
