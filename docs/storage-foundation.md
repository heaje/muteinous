# Result storage foundation (M1.7)

This describes the internal implementation of [Issue #22](https://github.com/heaje/muteinous/issues/22), under D105–D112, D123–D131 and D160 of the [canonical decisions](architecture/decisions.md). It does not establish a scan serialization format, cache policy, or native installation staging mechanism.

## Boundaries and use

[ResultStore](../src/muteinous/infrastructure/storage/bundles.py) accepts an existing, private, application-controlled local root. Do not use a game directory, a user-selected data directory, or an installation staging directory. The caller owns root creation and OS permissions. Logical result keys are bounded lowercase identifiers; job and validity identities are opaque strings. The caller is responsible for deriving actual source/configuration identities, supplying a read-only domain validator that raises on failure, and coordinating authoritative generation changes with publication. No plugin interface is required.

- On startup call `cleanup_abandoned()`; inspect its retained entries and reasons. No startup hashing of all results.
- Capture `selection(result)` before producing a result. Use `with store.stage(job_id, minimum_bytes=..., estimate_bytes=...) as area` to obtain a private payload directory on the destination filesystem. All staging access, including worker activity, must finish before releasing the owning context. Do not hand the path to independently surviving external readers/processes. Do not write bundle metadata yourself.
- Write only into the private payload. Use `area.space_assessments` for advisory uncertainty warnings. Include any additional simultaneous temporary/destination requirements in `other_requirements`. A known minimum shortage refuses work; unknown upper estimates are allowed cautiously. A failed free-space measurement refuses rather than guessing. No reservation, background monitoring or cache deletion occurs. ENOSPC/EDQUOT and Windows disk-full errors during the staging context or publication are reported as insufficient space; other I/O failures propagate.
- Call `publish` with the captured expected selection, current source/configuration/generation, domain validator and final authoritative freshness callback. The callback must be synchronized by the caller with changes to those dependencies and must not recursively acquire the storage guard. Stale producers cannot replace a newer manifest. The storage layer cannot derive source freshness by itself.
- Use `with store.open_current(...) as path` for read-only access. It validates the exact manifest-selected bundle against expected identities, deterministic integrity metadata and domain validity before exposing it. All reuse rehashes; no session verdict exists to become stale (D127–D128 optimization not implemented). Readers must not modify published files. No published bundle is deleted by this component, including orphan candidates and superseded versions, so old readers are protected without a reference counter.

## Publication and recovery

The directory layout separates `staging/<unique-id>/payload`, `bundles/<unique-id>`, `current/<logical-result>.json`, and persistent `stage-leases`. An ownership marker binds the stage, job, process and session to a matching unique lease file. The stage lease remains held for the entire context and is automatically released by the OS if its process exits. Cleanup acquires the exact lease before deleting a tree; PID age/reuse is not evidence. A missing, mismatched or locked lease, malformed marker, unrelated name, unexpected staging-root entry, link, nonregular entry or inaccessible directory prevents cleanup. Small lease files are intentionally retained so their identity is never reused or unlinked while another process could open them.

Bundle metadata `integrity.json` is UTF-8 canonical JSON (sorted keys, compact separators, no BOM or nonfinite values); records are sorted by exact slash-separated relative path and contain logical length and SHA-256. The current manifest binds the exact bundle ID and SHA-256 of the canonical metadata bytes. Exact comparison against a freshly enumerated inventory rejects invalid schemas/types, duplicate or missing records, unexpected files/empty directories, unsafe paths, and changed contents. Reserved and ambiguous names, links/reparse points, nonregular entries and unexpected filesystem boundaries are refused. Hashes establish consistency, not authenticity against deliberate tampering.

After private validation, the directory is atomically renamed to a new bundle ID. The candidate is revalidated in its committed directory and its authoritative source/configuration/generation and expected prior selection checked inside the exclusive selection guard; only then is the small current manifest atomically replaced. A failed directory rename or failed manifest switch leaves the previous selection untouched. A directory without a valid current reference is never inferred to be authoritative. After interruption or power loss, missing/damaged manifests or referenced bundles fail on demand; no fallback, guessed repair or automatic job resumption. Authorized regeneration of validly selected results is possible; recovery of a malformed manifest requires a separate explicitly authorized recovery operation. **No power-loss durability guarantee.**

## Filesystem and concurrency limits

The implementation uses standard-library same-filesystem `os.rename`, `os.replace`, and OS exclusive file leases (Windows byte-range locking; POSIX flock). Publication and abandoned cleanup are fail-closed unless the caller explicitly establishes local filesystem support for these semantics via `atomic_rename_supported=True`. The flag covers both atomic visibility and reliable local exclusive leases; it is not inferred from a successful disk-space query or a filename. Target local Windows NTFS; ordinary local POSIX filesystems with equivalent semantics are candidates for portability. Network shares, unknown/removable filesystems, and cross-device publication are not established as supported. Platform/filesystem capability detection and actual Windows/macOS/Linux verification remain integration/review obligations. Staging is always on the destination filesystem; this API does not import already-published external bundle directories or move them across filesystems. A future external producer must copy into a private destination stage and independently verify the complete copied data and metadata under D109, never publish by cross-device move.

Selection guard contention fails safely and may be retried by the caller. Basic controlled-root checks do not promise immunity to malicious check-then-open races (D131). Native installation staging remains distinct. Do not introduce cleanup of published versions until D111–D112 reader acquisition/release and cleanup exclusion, external-use uncertainty and other references are implemented. D113–D122 optional cache classification, LRU/budget accounting, safe eviction and expedited cleanup/recheck remain outstanding; retaining superseded/orphan bundles is the intentional safe interim behavior. No optional cache deletion is attempted for space pressure.
