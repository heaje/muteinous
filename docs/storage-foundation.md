# Result storage foundation (M1.7)

This describes the internal implementation of [Issue #22](https://github.com/heaje/muteinous/issues/22), under D105–D112, D123–D131 and D160 of the [canonical decisions](architecture/decisions.md). It does not establish a scan serialization format, cache policy, or native installation staging mechanism.

## Boundaries and use

[ResultStore](../src/muteinous/infrastructure/storage/bundles.py) accepts an existing, private, application-controlled local root. Do not use a game directory, a user-selected data directory, or an installation staging directory. The caller owns root creation and OS permissions. Logical result keys are bounded lowercase identifiers; job and validity identities are opaque strings. The caller is responsible for deriving actual source/configuration identities, supplying a read-only domain validator that raises on failure, and coordinating authoritative generation changes with publication. No plugin interface is required.

- Call `cleanup_abandoned()` on startup and inspect its retained entries and reasons. It is safe to call at any time: live owners are protected by their OS-held lease. Callers may also run it after jobs finish to reclaim abandoned staging space; no startup hashing of all results is performed.
- Capture `selection(result)` before producing a result. Use `with store.stage(job_id, minimum_bytes=..., estimate_bytes=...) as area` to obtain a private payload directory on the destination filesystem. **Before calling `publish()`, stop every writer/worker using the payload and close its files.** Finish all remaining staging access before leaving the owning context. Do not hand the path to independently surviving external readers/processes or write bundle metadata yourself.
- Write only into the private payload. Use `area.space_assessments` for advisory uncertainty warnings. Include any additional simultaneous temporary/destination requirements in `other_requirements`. A known minimum shortage refuses work; unknown upper estimates are allowed cautiously. A failed free-space measurement refuses rather than guessing. No reservation, background monitoring or cache deletion occurs. ENOSPC/EDQUOT and Windows disk-full errors during the staging context or publication are reported as insufficient space; other I/O failures propagate.
- Call `publish` with the captured expected selection, current source/configuration/generation, domain validator and final authoritative freshness callback. The callback must be synchronized by the caller with changes to those dependencies and must not recursively acquire the storage guard. Stale producers cannot replace a newer manifest. The storage layer cannot derive source freshness by itself.
- Use `with store.open_current(...) as path` for read-only access. It validates the exact manifest-selected bundle against expected identities, deterministic integrity metadata and domain validity before exposing it. It yields an ordinary path for caller-convention read-only use and holds no lifetime pin or reader reference. All reuse rehashes; no session verdict exists to become stale (D127–D128 optimization not implemented). Readers must not modify published files. No published bundle is deleted by this component, including orphan candidates and superseded versions. Implement D112 reader-reference acquisition before adding any published-bundle reclamation.

## Publication and recovery

The directory layout separates `staging/<unique-id>/payload`, `bundles/<unique-id>`, `current/<logical-result>.json`, and persistent `stage-leases`. An ownership marker binds the stage, job, process and session to a matching unique lease file. The stage lease remains held for the entire context and is automatically released by the OS if its process exits. A successfully published or failed stage leaves its staging directory (owner marker and any unpublished payload) and its small lease file until a later `cleanup_abandoned()`; lease files persist by design so their identity is never reused or unlinked while another process could open them. Cleanup acquires the exact lease before deleting a tree; PID age/reuse is not evidence. A missing, mismatched or locked lease, malformed marker, unrelated name, unexpected staging-root entry, link, nonregular entry, inaccessible directory, or alternate data stream prevents cleanup. Cleanup reports such a stage as retained rather than deleting a tree whose ownership or inventory is ambiguous.

Bundle metadata `integrity.json` is UTF-8 canonical JSON (sorted keys, compact separators, no BOM or nonfinite values); records are sorted by exact slash-separated relative path and contain logical length and SHA-256. The current manifest binds the exact bundle ID and SHA-256 of the canonical metadata bytes. Exact comparison against a freshly enumerated inventory rejects invalid schemas/types, duplicate or missing records, unexpected files/empty directories, unsafe paths, and changed contents. Reserved and ambiguous names, links/reparse points, nonregular entries and unexpected filesystem boundaries are refused. Hashes establish consistency, not authenticity against deliberate tampering.

On Windows, bundle inventory enumerates streams for each file and directory visited by the inventory walk and rejects NTFS alternate data streams other than the default `::$DATA` stream. Only `ERROR_HANDLE_EOF` (38, no streams) and `ERROR_INVALID_PARAMETER` (87, observed for unsupported filesystems) on the initial enumeration are treated as empty; every other enumeration error fails closed. Abandoned-stage cleanup also walks each staging tree with this inventory traversal. A stage containing an alternate stream on any walked entry—including `owner.json`—is therefore conservatively retained and reported with the alternate-data-stream reason; its files are not deleted. Cleanup first reads `owner.json` through its default stream to validate the canonical marker, then the inventory walk also enumerates that file's streams. Current manifests and lease files are not stream-enumerated: they are read through their default streams and checked against the exact canonical manifest bytes or matching lease contents. This check does **not** inspect extended attributes (xattrs), resource forks, or other platform-specific metadata, so those are outside the bundle inventory and integrity guarantee.

After private validation, the exclusive selection guard is held briefly for expected-selection/freshness checks and the directory rename. The committed directory is then revalidated outside the guard. The guard is reacquired briefly for a final expected-selection/freshness check and the atomic current-manifest replacement. Freshness callbacks run only while the guard is held; bundle hashing and domain validation do not. Guard acquisition waits briefly for contention, then refuses retryably. Ordinary refusals before the directory rename (including initial-guard timeout and metadata/domain validation failure) leave the same stage retryable. Once renamed, the stage is consumed: post-rename validation failure, final-guard timeout, superseded refusal or a manifest-replacement error before commit leaves this attempt unpublished and may leave an unreferenced bundle. After any asynchronous `BaseException`, discard the stage and stage again rather than retrying it; interruption can leave publisher metadata behind before it is registered for cleanup.

The atomic current-manifest replacement is the **commit point**. An interruption before replacement completes leaves the previous selection authoritative. If replacement completed before an interruption (even before `publish()` returned), the new selection may be authoritative although the call raised. When the outcome is ambiguous, reread `selection()`; do not assume either version. `publish()` validates a snapshot and requires all payload writers/workers to have stopped and closed their files before it is called. A writer changing the payload during publication—including after committed-bundle validation and before manifest replacement—violates the caller contract; this component does not defend against that D131 race. Every `open_current()` rehashes the selected bundle and refuses detected later modifications rather than silently using them. `open_current()` captures the manifest selection under the guard, validates the immutable bundle outside it, then rechecks that the selection is unchanged before yielding the path. If it changed during validation, the open is refused. A directory without a valid current reference is never inferred to be authoritative. After interruption or power loss, missing/damaged manifests or referenced bundles fail on demand; no fallback, guessed repair or automatic job resumption. Authorized regeneration of validly selected results is possible; recovery of a malformed manifest requires a separate explicitly authorized recovery operation. **No power-loss durability guarantee.**

## Filesystem and concurrency limits

The implementation uses standard-library same-filesystem `os.rename`, `os.replace`, and OS exclusive file leases (Windows byte-range locking; POSIX flock). Publication and abandoned cleanup are fail-closed unless the caller explicitly establishes local filesystem support for these semantics via `atomic_rename_supported=True`. The flag covers both atomic visibility and reliable local exclusive leases; it is not inferred from a successful disk-space query or a filename. Target local Windows NTFS; ordinary local POSIX filesystems with equivalent semantics are candidates for portability. Network shares, unknown/removable filesystems, and cross-device publication are not established as supported. Platform/filesystem capability detection and actual Windows/macOS/Linux verification remain integration/review obligations. Staging, `bundles/`, and `current/` must share a device; stage creation verifies this before creating a stage directory or lease, and publication checks it again. Staging is always on the destination filesystem; this API does not import already-published external bundle directories or move them across filesystems. A future external producer must copy into a private destination stage and independently verify the complete copied data and metadata under D109, never publish by cross-device move. On Windows, unprefixed caller roots whose paths exceed the OS path limit are unsupported; callers must provide an extended-length `\\?\`-prefixed root. The storage API does not normalize caller paths into or out of that extended-length form.

Selection-guard acquisition waits briefly before refusing retryably. A refusal before rename leaves the stage retryable; a failure after rename consumes it and can leave a retained unreferenced bundle. The caller-established storage root and paths inside it are checked for links/reparse points; links in ancestors above that root are outside the controlled boundary and are not rejected. Any `..` path component is refused before normalization. Basic controlled-root checks do not promise immunity to malicious check-then-open races (D131). Native installation staging remains distinct. Do not introduce cleanup of published versions until D111–D112 reader acquisition/release and cleanup exclusion, external-use uncertainty and other references are implemented. D113–D122 optional cache classification, LRU/budget accounting, safe eviction and expedited cleanup/recheck remain outstanding; retaining superseded/orphan bundles is the intentional safe interim behavior. No optional cache deletion is attempted for space pressure.
