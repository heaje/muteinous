# WP2 — whisper.cpp backend research

**Scope:** documentation/source review only; upstream `ggml-org/whisper.cpp` at CI pin `96ec4d9823e9d0211944172da35f9f29134af990` (reported as `1.9.6-dev`) and latest release as of 2026-11-26. No build, SDK install, binary/model download, device enumeration, or inference was performed. Links point to the pin unless noted.

## Findings

### Builds, device support and packaging

- **CPU runtime dispatch:** `GGML_BACKEND_DL=ON` builds backends as dynamically loaded libraries and requires `BUILD_SHARED_LIBS=ON`; `GGML_CPU_ALL_VARIANTS=ON` requires backend-DL. Use `-DGGML_NATIVE=OFF -DGGML_BACKEND_DL=ON -DGGML_CPU_ALL_VARIANTS=ON` for portability; `GGML_NATIVE` is incompatible with backend-DL. x86 builds feature variants and runtime feature detection, including AVX2/AVX-512 options. This is not an AVX-512-only binary. Windows/MSVC variant coverage has compiler limitations and needs exact build validation.
- **Vulkan:** `-DGGML_VULKAN=ON`. CMake requires Vulkan components including `glslc` and SPIR-V headers and generates shaders. Install/configure Vulkan SDK on build runner. Runtime requires suitable Vulkan driver; no vendor SDK at runtime. Backend enumerates Vulkan physical devices.
- **HIP/ROCm:** `-DGGML_HIP=ON -DAMDGPU_TARGETS=gfx1100` (or `-DCMAKE_HIP_ARCHITECTURES=gfx1100`). Requires HIP, hipBLAS, rocBLAS, HIP >=6.1 and ROCm toolchain. Pinned ggml CMake states CMake on Windows does not support HIP language; its `hipcc` workaround is not evidence of a supported hosted Windows build. Treat HIP on windows-2025 as infeasible absent a verified SDK/runner; build on ROCm Linux or confirmed self-hosted Windows. `gfx1100` corresponds to RX 7900 XTX in README; machine inventory identifies target RX 7900 XT as gfx1100, but no local test (L1 only).
- **Intel:** `-DGGML_SYCL=ON` enables SYCL (default `GGML_SYCL_TARGET=INTEL`) and needs Intel oneAPI/SYCL toolchain and runtime. `-DGGML_OPENVINO=ON` enables ggml OpenVINO backend; Whisper encoder integration additionally uses `-DWHISPER_OPENVINO=ON`, requires OpenVINO package/runtime plus generated encoder IR `.xml/.bin`. OpenVINO supports supported CPU/Intel GPU devices, but it is not equivalent to whole-model SYCL offload.
- **NVIDIA:** `-DGGML_CUDA=ON`, NVIDIA CUDA Toolkit/compiler and compatible driver/runtime. `CMAKE_CUDA_ARCHITECTURES` may target architectures. CUDA is separate from vendor-neutral Vulkan.
- **One distribution for CPU/NVIDIA/AMD/Intel?** Backend-DL enables a shared core with backend modules, and CPU ISA variant selection. A distribution can in principle include multiple backends and load what is available, but backend-DL doesn't supply missing driver/vendor runtime dependencies, remove ABI/CRT and licensing concerns, guarantee optimal selection, or assure all devices support all ops. Vulkan is broadest plausible GPU option; CUDA/HIP/SYCL/OpenVINO are optional runtime-specific bundles. Package/test discrete configurations and implement diagnostics/selection rather than promise one turnkey portable binary.
- **Enumeration/selection:** whisper-cli calls `ggml_backend_load_all()`. CLI has `--no-gpu` (`-ng`) and `--device N` (`-dev`, default 0); `WHISPER_ARG_DEVICE` also sets the index. `whisper_context_params` exposes `use_gpu` and `gpu_device` (header comment says CUDA device); VAD context params have these too. OpenVINO encoder has `--ov-e-device`/device string (e.g. CPU/GPU). ggml registry/device APIs enumerate loaded backends. There is no single general Whisper C API backend/vendor selector; do not assume index meaning is identical across backends. `GGML_VK_VISIBLE_DEVICES` filters Vulkan device visibility; `HIP_VISIBLE_DEVICES` is ROCm/HIP runtime visibility (set before process start).
- **Explicit GPU unavailable:** `--device` is an index, not an explicit backend assertion. `use_gpu=false` opts out; ggml scheduler can assign unsupported ops to CPU. Sources reviewed do not settle whether a missing requested index/backend hard-fails or transparently falls back in every case. Don't claim always silent fallback or always error. A successful transcription/index alone does not prove GPU use; inspect backend logs/telemetry. Application can provide strict-GPU policy if fallback must be prohibited.

### Timing, models and Python

- **Word timestamps:** Experimental `-ml 1`/`--max-len 1` makes output segments approximately word-sized, potentially with punctuation; it is not a dedicated word aligner. `--output-words`/`-owts` produces a karaoke script and is not a structured transcript API (font/ffmpeg assumptions). API supports experimental token timestamps; `-dtw <model>` enables DTW token timestamps using model-specific alignment-head presets. Use API token data (`whisper_full_get_token_data`) or full JSON output for structured token-level results, and validate boundary quality empirically. VAD uses `--vad` plus `-vm` model and has threshold, minimum speech/silence, maximum speech duration, speech padding and overlap options. VAD segments audio and is not word alignment; map resulting times carefully.
- **Quantization/turbo:** README documents ggml model quantization, example `q5_0`; ggml quantizer supports common Q4/Q5/Q8 and K-quant families. Read exact supported quantization names from pinned quantize CLI rather than assume all formats apply to Whisper. README includes `large-v3-turbo`; API alignment preset `WHISPER_AHEADS_LARGE_V3_TURBO` exists. Model support is L1, not quality/performance validation.
- **Python options:** no first-party Python binding in repo's bindings list. Third-party `pywhispercpp` (Pybind11), ctypes to C API in `include/whisper.h` (ABI/lifetime care), or `whisper-cli` subprocess. Subprocess is simplest integration boundary; JSON output can carry results. For Python-first app, subprocess or a small focused ctypes wrapper are plausible.

### Licensing and size

- Project code is MIT; preserve upstream notices. CUDA, ROCm, Vulkan SDK/runtime, oneAPI, OpenVINO, MSVC/OpenMP and other included runtime components have separate redistribution/deployment terms. Windows shared builds may contain whisper, ggml core/base/CPU and backend DLLs plus compiler/OpenMP/vendor runtime DLLs. Audit actual dependencies (`dumpbin /DEPENDENTS`) per built bundle; do not assume static linking/redistribution rights.
- **Binary size:** no reliable pinned source table provides per-backend executable/DLL sizes; size depends on compiler, debug symbols, static/DL, CPU variants and backend. Mark **unmeasured**, rather than invent figures. CPU-only smallest; all-variants adds modules; Vulkan adds backend/shaders; CUDA/HIP add backend and depend on large external runtimes; SYCL/OpenVINO distributions are runtime dominated. Models separate: README rough sizes tiny 75 MiB, base 142 MiB, small 466 MiB, medium 1.5 GiB, large 2.9 GiB. No weights downloaded.

## Summary (<400 words)

L1 documented support: whisper.cpp 1.9.6 supports CPU, Vulkan, CUDA, HIP/ROCm, SYCL and OpenVINO paths; portable CPU variants require backend-DL and all-variants. Vulkan needs Vulkan SDK components including `glslc`. HIP needs ROCm/HIP >=6.1 and pinned CMake documents Windows HIP language limitations, so Windows-hosted HIP should not be promised without verified tooling. Backend DLLs can coexist conceptually but do not eliminate vendor runtimes, drivers, licensing or dispatch uncertainties. CLI/API expose GPU enable/index; OpenVINO has encoder device string. Unavailable-device strictness is not established by reviewed source. Experimental token/DTW timestamps are available; VAD is separate. `large-v3-turbo` is supported in docs/API. MIT project licensing does not cover all included runtimes. Binary sizes unmeasured.

Commands run: none (raw upstream documentation/source fetches only). Wall-clock: approximately 15 minutes. No L2–L5 evidence; no inference. Blockers: confirm exact CLI device-listing flag and unavailable-device behavior in a permitted runtime test; measure payload sizes with release builds. No maintainer approval required for this research; approval required before L5 ASR inference under common instructions.
