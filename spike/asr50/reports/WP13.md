# WP13 — ONNX Runtime Whisper small.en

## Result

DirectML works with the approved `whisper-small-en-onnx-fp16` export on the RX 7900 XT using `onnxruntime-directml==1.24.4`, `device_id=0`, `enable_mem_pattern=False`, and `ORT_SEQUENTIAL`. The earlier blocker report was mistaken: the valid-id session succeeded. The graph-optimizer error happened only on an invalid-device request when ORT retried the CPU EP in that DirectML environment. All three graphs also create sessions in WindowsML ORT 1.30.1 (which warns `Init provider bridge failed.`) and CPU ORT 1.32.0.

## Failure and fallback tests

- Invalid device id 999 emitted: `887A0002 The object was not found. If calling IDXGIFactory::EnumAdaptes, there is no adapter with the specified ordinal.` ORT then logged `Falling back to ['CPUExecutionProvider'] and retrying.` The retry failed with the graph error: `GetIndexFromName itr != node_args.end() was false. Attempting to get index by a name which does not exist:InsertedPrecisionFreeCast_/layers.3/final_layer_norm/Constant_output_0for node: /layers.0/self_attn_layer_norm/Mul/SimplifiedLayerNormFusion/`. Thus fallback was explicit in logs, not silent. The valid id 0 path is unaffected.
- `session.disable_cpu_ep_fallback=1` together with explicit providers `[DmlExecutionProvider, CPUExecutionProvider]` fails immediately: `Conflicting session configuration: explicitly added the CPU EP to the session, but also disabled fallback to the CPU EP via session configuration options.`
- With the CPU EP removed and fallback disabled, session creation fails because the graph contains CPU-assigned nodes: `This session contains graph nodes that are assigned to the default CPU EP, but fallback to CPU EP has been explicitly disabled by the user.` This matches the mixed-provider profile; this export cannot be made all-DML by that flag.
- No optimizer workaround was needed for valid id 0, so no optimizer bisect was conducted. PyPI reports `onnxruntime-directml` latest as 1.24.4 and metadata includes Python 3.14; no newer cp314 wheel was available to test at access time.

### Long/non-speech loop policy

Compared policy on/off on 30 clips per device: all long clips (including >30-second natural sentences) plus all 20 silence/non-speech clips. “On” means repeated-four-token-sequence detection (stop after two repeats) and per-chunk cap `min(444, 10 + ceil(10 × chunk_seconds))`; “off” disables loop detection and uses the Whisper 444-token hard maximum. Every one of the 40 generated chunks per device/mode stopped on EOS; there were zero loop-detector stops, zero token-cap hits, and the maximum was 87 generated tokens. No runaway repetition occurred in this sample, even with policy off. Several non-speech clips still hallucinated short outputs (including “you” and, for some noise clips, longer phrases); policy on/off had the same stop results. Token counts and stop reasons are in JSONL records with `run.kind` `policy-test-on` / `policy-test-off`.

### Deletion investigation

The earlier v2 102 deletion total is reproduced from the saved v2 raw outputs (WER 0.1233, S/D/I 36/102/11); this experiment found no runner bug, so those results do not change. Deletions concentrate in `natural_sentences_00` (17) and `natural_sentences_01` (73), plus `natural_35s_00` and `natural_42s_00` (6 each). The decoder is fed actual float32 `(1,80,3000)` features; longer clips are represented by exact, non-overlapping chunk ranges. The generation config inserts `<|notimestamps|>` at decoder position 1; configured suppress tokens do not include EOS, and generated timestamp tokens are not being used.

The worst case, `natural_sentences_01`, has chunk stats `87/eos`, `80/eos`, `1/eos`, `41/eos` tokens for ranges 0–30, 30–60, 60–90, and 90–104.831 seconds; no chunk reached its corresponding cap (310, 310, 310, 159). Its 60–90-second PCM chunk is not silent (10-second RMS windows 0.0905–0.0971), but the model emits one token then EOS; WER alignment accounts for the 73 deleted words in that clip. Both DML and CPU reproduce this behavior. This is early model EOS on an acoustically active chunk, not input truncation, cap exhaustion, timestamp suppression, or incorrect input shape. Other high-deletion chunks also stop at EOS below cap. Fixed 30-second chunking can reset context at boundaries, but no implementation error was found to fix; prior v2 results remain valid as measured.
