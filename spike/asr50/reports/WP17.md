## ORT enumeration and versions

Both wheels' `ort.get_ep_devices()` exposed CPU and DML `OrtEpDevice` entries. The EP wrapper exposes `ep_name`, `ep_metadata`, `ep_options`, `ep_vendor`, `memory_info`, `create_sync_stream`; `.device` exposes `device_id`, `metadata`, `type`, `vendor`, `vendor_id`. For DML, both reported AMD RX 7900 XT, vendor ID 4098 / device ID 29772, `DxgiAdapterNumber=0`, `DxgiVideoMemory=20420 MB`, `Discrete=1`, `LUID=91308`. CPU metadata had only its description. These match the device metadata observed in WP3; keys use PCI identity plus normalized name, not index/LUID. Invocation index is kept separately.

The Windows ML import warned on stderr:

```text
Init provider bridge failed.
```

The guard does not interpret the warning as an EP/device failure. In a profiled run the colored warning text also preceded the JSON event list in ORT's profile output; the prototype scans for the JSON array rather than assuming the file starts with JSON. Despite the warning, that wheel listed DML and CPU, enumerated adapter metadata, passed valid DML encoder execution/profile verification, and rejected invalid device 9999. This verifies the wheel's bundled ORT DirectML EP path, not Windows ML catalog-acquired EPs.

## Encoder mismatch resolved

Inspection of the approved `encoder_model_fp16.onnx` graph with ONNX found input `input_features`, element type `FLOAT` (float32), dimensions `['batch_size', 'feature_size', 'encoder_sequence_length']`. The correct feed is float32 `(1, 80, 3000)`; the `fp16` filename describes model weights/compute, not this input tensor's dtype.

The first guard implementation mapped the symbolic feature dimension to 1, so it fed `(1,1,3000)`. DirectML then failed at `/conv1/Conv` with `80070057 The parameter is incorrect`. The cause was the malformed input, not a profiling setting or retry behavior. The guard now sets symbolic feature size to 80 and sequence length to 3000. It uses WP13's session options (`enable_mem_pattern=False`, `ORT_SEQUENTIAL`) and providers DML device 0 plus CPU. The corrected encoder forward succeeded with **380 DML profile events** on ORT 1.24.4; equivalent test passed on Windows ML ORT 1.30.1.202610302006. Explicit GPU invalid-device tests raise a typed guard error on both wheels. No optimizer workaround is needed for valid device 0.

## Enforcement and runtime behavior

* CPU mode constructs CPU-only. Auto prefers DML and records CPU fallback reason on failed creation, absent DML or failed probe. Explicit-GPU configures `device_id`, rejects a CPU-only session, disables runtime EP retry, runs a forward, and requires DML events. Profile proof is stronger than provider listing, but does not expose adapter identity; identity is associated through the requested adapter option and enumeration.
* Synthetic MatMul explicit-GPU/auto tests and real encoder explicit-GPU test passed. Encoder real-model DML execution is **L4**; whisper.cpp approved small.en q5_1 explicit Vulkan inference is **L5**.
* Invalid `device_id=9999` in ORT 1.24.4 DML-only construction was observed to retry CPU (`Falling back to ['CPUExecutionProvider'] and retrying.`). Guard checks actual providers and raises rather than accepting it. Invalid-device tests passed on both ORT distributions. DML-only and DML+CPU fallback behavior is tested.
* whisper.cpp preflights through `ggml-diag list`, uses `-dev <index>` for explicit/auto GPU and `-ng` for CPU, then checks stdout/stderr backend markers. It rejects missing/hidden GPU indices. `GGML_VK_VISIBLE_DEVICES=99` made diagnostics report CPU only and explicit index 0 was rejected before whisper-cli.

Partial placement policy decision: explicit GPU may allow CPU shape/control operators, but requires DML events and all heavy MatMul/Conv nodes on DML; report provider counts. This prototype reports DML profile event count but does not yet map every event to the full graph's heavy-op inventory. Treat this as a lower-bound L4 check, not production-grade validation of partial placement.

Reliable signals: ORT profile provider events and ggml diagnostic inventory plus post-run backend evidence. Fragile signals: whisper.cpp log strings (`using Vulkan0 backend`, `Vulkan0 total size`, `CPU total size`, `no GPU found`) can change across versions/log levels. Production runtimes should expose structured requested/actual adapter identity, per-node provider placement and fallback reason.
