# Installation discovery

D132–D133 and D137–D138: candidate locations and names are untrusted launcher metadata, not support or installation authorization. Manual folder intake is independent of launchers. The discovery and manual-intake functions do not open game content. Invoke the lightweight probe separately when useful. A comprehensive scan is a distinct operation requiring explicit user initiation (D138).

Windows sources: Steam HKCU SteamPath, HKLM InstallPath (both registry views), conventional ProgramFiles roots, modern and legacy libraryfolders.vdf (config first, steamapps fallback when absent) and appmanifest ACF; Epic ProgramData/Epic/EpicGamesLauncher/Data/Manifests .item JSON; GOG HKLM/HKCU Software/GOG.com/Games registry records (both views). No game catalog is used. [Steam data format](https://reverseengineering.wiki/index.php/Format:Steam_client_data_files) supports the ACF and modern VDF structure; [SKIF Steam library discovery](https://github.com/SpecialKO/SKIF/blob/master/src/stores/Steam/steam_library.cpp) corroborates both VDF locations and layouts; [observed launcher layouts](https://github.com/VantaCode420/SmartHdrManager/blob/main/Library.cs) support the Steam registry values, steamapps layout, Epic JSON fields and HKLM GOG path/gameName. Other registry views/hives are best-effort searches, not evidence of real registrations. [Epic documentation](https://dev.epicgames.com/documentation/en-us/unreal-engine/multiple-launcher-unreal-engine-installs) confirms the usual ProgramData root but documents relocated PCB-mode data, which is not discovered here. Actual launcher installations still require Windows validation.

Provisional implementation defaults, not new architectural requirements or benchmark-derived thresholds. These budgets keep automatic discovery lightweight and responsive; revisit their numeric values using real-installation performance and coverage evidence. They do not establish format support or constrain a separately requested comprehensive scan. Current limits: at most 4,096 processed discovery entries/records, 1 MiB per metadata file (plus a possible overflow-detection byte), 64 KiB per registry value and 16 MiB aggregate metadata budget (plus one possible final file overflow-detection byte). Failed registry reads with unspecified transfers conservatively charge the requested buffer. Directory enumeration may obtain one extra entry to detect truncation. Registry reads use a fixed buffer with [RegQueryValueExW](https://learn.microsoft.com/windows/win32/api/winreg/nf-winreg-regqueryvalueexw), refuse unsupported types and never resize on ERROR_MORE_DATA. A probe examines at most 128 entries at depth zero through two, requests at most four unbuffered bytes per ordinary file, and skips symlinks, reparse points and special files, including a linked probe root. OS read-ahead and check/open races are not controlled by these application limits. A STRM signature is only a provisional AST hint; a missing signature is not proof of absence. A probe's issues and truncation describe incomplete evidence. Canonical existing directories are deduplicated by exact resolved spelling rather than assuming case-insensitive equality; unresolved candidates are retained with availability status. Availability indicates directory evidence only, not launcher readiness. Metadata files and their immediate parent directories must be ordinary filesystem objects. Explicit parent traversal, malformed path strings and Windows device/reserved paths are refused. An Epic incomplete-install flag is reported, not proof of a playable installation. Oversized metadata and incomplete probes are marked truncated; discovery issues also describe invalid or inaccessible observations. Cancellation raises without publishing a partial result. Cancellation is cooperative between bounded operations; an already blocked OS call cannot be preempted. Discovery and probing do not write game or launcher metadata, hash or decode content, run ASR, or require additional dependencies.

Portable synthetic fixtures exercise metadata parsing, candidate deduplication, manual selection, errors, cancellation and probing. Windows-only tests exercise read-only registry-view selection with test doubles and the bounded native reader against a unique temporary synthetic HKCU key (created and deleted only by the test). They are not verification against a physical installation. See [issue #51](https://github.com/heaje/muteinous/issues/51) and [PR #57](https://github.com/heaje/muteinous/pull/57) for revision-specific verification and review evidence. Synthetic success does not establish real-installation compatibility.
